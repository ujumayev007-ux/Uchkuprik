# Security

## Configuration and transport

- Zod validation rejects missing/invalid environment configuration and reports field names without secret values.
- Local secrets (database password, `APP_SECRET_KEY`) are generated by `npm run setup:env` into the ignored `.env`; existing values are never overwritten.
- Production requires HTTPS for `APP_ORIGIN` and `sslmode=verify-full` for PostgreSQL.
- Helmet headers, no-store responses, strict browser-origin allowlist, bounded timeouts. `TRUST_PROXY` sets the exact number of trusted proxy hops (0 by default, 1 on Render) so `req.ip` cannot be spoofed.
- Logs contain request IDs, statuses, durations and error class/driver codes only, never URLs, bodies, credentials or raw driver messages.

## Identity and sessions (Phase 2)

- **Passwords**: scrypt (N=2^15, r=8, p=1, per-hash salt, parameters stored with the hash). Policy: 10-128 characters with a letter and a digit. Unknown users are checked against a dummy hash so response time does not reveal valid usernames.
- **PINs**: 4 digits, scrypt over an HMAC of `userId:pin` keyed by a key derived (HKDF) from `APP_SECRET_KEY`, so a database leak alone does not allow offline brute force of the 10 000 PIN space. PIN login only works from a **registered device** (httpOnly device cookie, hash stored server-side) and only for staff assigned to that device's branch.
- **PIN limits**: PIN sessions can never pass the step-up check, so they cannot perform user, role, device or tenant administration regardless of role.
- **Lockout**: 5 failed password (or PIN) attempts lock that credential for 15 minutes, plus a per-IP credential rate limit (20/min). The general API limiter keys authenticated traffic by session so terminals behind one NAT do not starve each other.
- **Sessions**: 256-bit random opaque tokens in `HttpOnly; SameSite=Strict` cookies (`__Host-` prefix and `Secure` in production). Only the SHA-256 hash is stored. Idle timeout 60 min (password) / 30 min (PIN), absolute 12 h / 14 h. Revoked on logout, password change/reset, PIN reset, user disable and device revoke; tenant suspension blocks all sessions immediately.
- **MFA**: RFC 6238 TOTP. Secrets are AES-256-GCM encrypted with a key derived from `APP_SECRET_KEY`. Accepted time steps are persisted so a code cannot be replayed. Mandatory for platform administrators; tenants can require it for privileged roles (`requireMfaForAdmins`).
- **Step-up**: user, role, device, branch-creation and platform-tenant changes require password (+TOTP when enrolled) re-authentication within the last 5 minutes.
- **CSRF**: SameSite=Strict cookies, rejection of any foreign `Origin`, JSON-only bodies.

## Authorization

- Permissions are stable keys (`backend/src/modules/auth/permissions.ts`); roles hold permission sets per tenant; seven system roles are seeded per tenant.
- Every endpoint enforces permissions server-side from the session; tenant IDs are never accepted from the client.
- Anti-escalation: non-owners can only grant or edit permissions they hold, cannot assign the owner role and cannot manage users holding permissions they lack. The owner role is immutable and at least one active owner must remain.
- Branch scope: users have all-branch access or explicit branch assignments; branch switching, device registration and user assignment verify it.
- Composite `(tenantId, id)` foreign keys on user-role, user-branch and device-branch relations make cross-tenant references impossible in the database.

## Audit

`audit_logs` is append-only: a trigger rejects UPDATE, DELETE and TRUNCATE. Login successes/failures, lockouts, MFA, re-authentication and every administrative change are recorded with actor, tenant, IP and request ID, never secrets, hashes or PINs.

## Pending

In-memory rate limiting is per process (move to Redis when scaling horizontally). `APP_SECRET_KEY` rotation with re-encryption is not automated yet. Backups, encryption at rest, intrusion detection and compliance certification depend on deployment infrastructure. This document does not certify production, payment, fiscal or legal compliance.

## Financial controls (Phase 4)

Server-side pricing only; idempotent order and payment creation; order row locks prevent double charges (tested with concurrent requests); database constraints make overpayment and over-refund impossible; payment, refund, cash-movement and order-event rows are immutable; refunds require `payments.refund` plus password re-authentication; cash refunds leave the refunding register's shift; cancellations of paid orders require a full refund first; discounts, cancellations and refunds are audited. Internal costs appear only for `finance.view`. Receipts are explicitly marked non-fiscal until an authorized fiscal provider is integrated.

## Real-time and printing (Phase 5)

WebSocket handshakes use the same session/device-cookie validation as HTTP, reject foreign origins, join only the session's tenant and active-branch rooms, and are revalidated every minute (revoked sessions are disconnected). Events carry identifiers and statuses only. Kitchen roles no longer hold `orders.view`; kitchen tickets and the queue screen contain no prices. Printer addresses are limited to private LAN IPv4 and raw-print ports to prevent server-side request forgery against loopback, cloud metadata or public hosts.
